# Farm Twin — Proof of Concept

**Team 5 Terra Minds | SDG 2: Zero Hunger | Course 2IRR10 | TU/e**

---

## What this PoC is

The Farm Twin proposes autonomous robots that detect Striga-infested zones
(spray herbicide) and low-NPK zones (apply fertilizer) on Kenyan maize farms.
Each robot is governed by a **Digital Entity** that mirrors the robot's
state and decides what to do next.

In this PoC the two entities are:

- **Physical Entity (PE):** a TurtleBot3 Burger inside a Gazebo simulation of
  the farm (`worlds/new_world.world`). It carries a LiDAR, drives under Nav2,
  and triggers `spray` / `fertilize` actions when it reaches a farm zone.
- **Digital Entity (DE):** a browser-based web interface that subscribes to
  every relevant ROS topic and renders the farm + robot live on an HTML
  canvas — the same view a remote operator would see.

The simulator stands in for the real robot, the web interface stands in for
the operator-facing dashboard, and the link between them (ROS 2 topics → an
in-process HTTP server → the browser) is the digital twin.

## Running in Docker (Windows + WSL2)

Start the container with `-p 8080:8080` so the web server's port is
forwarded from the container to the WSL2 host. WSL2 then proxies that
to Windows automatically, so a Windows browser hits the page at
`http://localhost:8080`:

```bash
docker run --rm -it --name turtlebot3_container -p 8080:8080 \
  -e DISPLAY=$DISPLAY \
  -v /tmp/.X11-unix:/tmp/.X11-unix \
  -v /home/c2irr10/turtlebot3_ws:/ws \
  --user $(id -u):$(id -g) turtlebot3_ws bash
```

X11 (Gazebo/RViz GUI) still works because the X server's Unix socket
is mounted in via `/tmp/.X11-unix`, which is filesystem-level and
doesn't depend on host networking. If you also need ROS 2 nodes
outside the container to discover nodes inside it, swap `-p 8080:8080`
back for `--net=host` — the two are mutually exclusive (Docker ignores
`-p` when host networking is active).

Every additional terminal joins the same container:

```bash
docker exec -it turtlebot3_container bash
cd /ws
source /opt/ros/jazzy/setup.bash
source /opt/turtlebot3_ws/install/setup.bash
source install/setup.bash
export TURTLEBOT3_MODEL=burger
```

### Reaching the web interface from your Windows browser

Inside the container, in a second terminal:

```bash
ros2 run farm_twin_poc web_server_node
# logs: web_server_node up — http://0.0.0.0:8080/
```

On Windows, open:

```
http://localhost:8080
```

That's it — `-p 8080:8080` puts the container's port 8080 on the WSL2
host, and WSL2 proxies localhost to Windows automatically.

If `localhost` doesn't work on older WSL2 setups, find the WSL IP from
a PowerShell window and use that instead:

```powershell
wsl hostname -I
# then in browser: http://<that-ip>:8080
```

To verify before troubleshooting Windows, hit the API from inside WSL:

```bash
curl http://localhost:8080/api/topics
```

## Step-by-step demo

The PoC has two launches — the **PE** (simulated robot + Nav2) and the
**DE** (orchestration + browser UI). Run them in separate terminals,
PE first, then drive the demo from the browser. The whole sequence
takes about a minute end-to-end.

### 1. Terminal A — start the Physical Entity

```bash
cd /ws
source install/setup.bash
export TURTLEBOT3_MODEL=burger
ros2 launch farm_twin_poc physical_entity.launch.py
```

**Wait** until the navigator logs:

```
[navigator_node] Nav2 is active. Awaiting /destination messages.
```

If you launched without `headless:=true`, a Gazebo window opens too and
you'll see the TurtleBot3 spawned at `(1.5, −2.0)` inside the farm.

### 2. Terminal B — start the Digital Entity

```bash
cd /ws
source install/setup.bash
ros2 launch farm_twin_poc digital_entity.launch.py
```

You should see the dispatcher, zone monitor, DT logger and web server
come up. The last line will be roughly:

```
[web_server_node] web_server_node up — http://0.0.0.0:8080/  ...
```

### 3. Browser — open the dashboard

Visit **http://localhost:8080**. Four panels show up:

| Panel | Position | Source | What it shows |
|---|---|---|---|
| **Mission**       | top-left     | `/dispatcher/status` + `/battery_state` | Battery, mission state, progress, waypoint list, Start button, battery override |
| **Actions**       | top-right    | `/dt/status`                | spray/fertilize counters + most-recent action log |
| **Twin Status**   | bottom-left  | `/navigator/status` + `/amcl_pose` + `/dt/status` | Robot state, position, current goal, twin sync error, zones visited |
| **Canvas**        | full screen  | baked map + `/amcl_pose`    | walls, zones, robot disc (138 mm) with heading indicator |

At this point the robot is sitting at spawn, AMCL has converged, and
the Mission panel reads:

```
Battery: 100% (12.6 V)
Status: Idle
Progress: 0 / 4
```

### 4. Click **Start Navigation**

The dispatcher publishes `WAYPOINTS[0]` on `/destination`, the navigator
drives to it, spins 360° at the zone, and acks. The browser updates
within ~33 ms (30 Hz SSE rate):

- **Mission panel**: Status turns blue ("Running"), Progress ticks
  `1 / 4`, the waypoint list grows a green ✓ for the completed zone and
  a blue → on the current one.
- **Actions panel**: a new row appears at the top — `SPRAY
  spray_zone_A 12:34:56`.
- **Twin Status**: Robot is "Navigating", Position updates live.
- **Canvas**: the blue disc moves from spawn to the zone, spins, settles.

The robot visits **A → B → D → C** (S-curve, shortest path). After the
last zone the Mission panel shows `Complete` (green), the Start button
re-enables, and the action log holds all four events.

### 5. Optional — test the low-battery return-home

This is the headline DT-vs-PE behaviour: the **dispatcher** watches
`/battery_state`; if it drops below 20 %, it stops the mission and
calls `/return_home` on the navigator. The robot drives back to
`(1.5, −2.0)` regardless of where it was in the tour.

Click **Start Navigation** again. While it's running:

1. In the Mission panel, type `15` into **Set battery** and press
   **Apply** (or hit Enter in the field).
2. Within ~1 second `battery_sim_node` snaps to 15 %, publishes on
   `/battery_state`, and the dispatcher catches it on its next callback.
3. The dispatcher logs:
   ```
   [DISPATCH] battery 15% < 20% — stopping mission and returning home
   ```
4. UI changes:
   - Mission status → **Aborted** (red)
   - Twin Status robot state → **Returning home** (bold orange)
   - The blue disc starts moving back toward spawn

When the robot reaches `(1.5, −2.0)` the navigator logs `[HOME]
reached`. Set the battery back to 100 % via the same input field and
click Start Navigation to run another tour.

### 6. Shutdown

`Ctrl-C` in Terminal B then Terminal A. The Gazebo window closes on
its own.

## Other ways to drive the system

| Action | UI button | Equivalent CLI |
|---|---|---|
| Start the mission | Mission panel → Start Navigation | `ros2 service call /start_navigation std_srvs/srv/Trigger` |
| Set battery to N % | Mission panel → Set battery + Apply | `ros2 topic pub --once /battery_set_level std_msgs/msg/Float64 "data: 15.0"` |
| Trigger return-home | (happens automatically below 20 %) | `ros2 service call /return_home std_srvs/srv/Trigger` |
| Stop the dispatcher only | — | `ros2 service call /stop_dispatch std_srvs/srv/Trigger` |
| Cancel an in-flight drive | — | `ros2 service call /stop_navigation std_srvs/srv/Trigger` |

## Useful launch overrides

```bash
# headless = Gazebo server only (no 3D GUI). Recommended on GPU-less
# machines (Docker-in-WSL, etc.) where the GUI starves the sim clock.
ros2 launch farm_twin_poc physical_entity.launch.py headless:=true

# pick a different spawn / map / world
ros2 launch farm_twin_poc physical_entity.launch.py \
    x_pose:=0.5 y_pose:=-2.5 map:=$HOME/my_map.yaml

# faster battery drain for short demo runs (default is 5%/h idle,
# 20%/h moving — too slow to hit the return-home threshold in a sim)
ros2 run farm_twin_poc battery_sim_node --ros-args \
    -p drain_per_hour_idle:=120 -p drain_per_hour_moving:=240

# change the low-battery threshold (default 20 %)
ros2 run farm_twin_poc mission_dispatcher_node --ros-args \
    -p return_battery_percent:=30
```

## Web server HTTP API

When the DE launch is up, `web_server_node` exposes:

```
GET  /                       -> web/index.html
GET  /api/state              -> all cached topics as JSON
GET  /api/state/<name>       -> one topic (e.g. /api/state/odom)
GET  /api/topics             -> list of cached topic names
GET  /api/stream             -> Server-Sent Events feed of state deltas
POST /api/start_navigation   -> forwards to /start_navigation Trigger srv
POST /api/set_battery        -> body {"percent": 0..100}, publishes Float64
```

Override host/port with `--ros-args -p host:=0.0.0.0 -p port:=8080`.

## After editing the world

`worlds/new_world.world` is the single source of truth for the walls and
zone positions. If you move things in it, regenerate the two derived
artifacts:

```bash
# 1) Nav2 occupancy grid for AMCL / costmap
python3 scripts/world_to_map.py worlds/new_world.world
# -> maps/new_world_map.{pgm,yaml}

# 2) Canvas geometry for the web interface
python3 scripts/world_to_canvas.py worlds/new_world.world
# -> web/map.json
# Then paste web/map.json into the MAP constant in web/app.js if you want
# the standalone (file://) mode to reflect the change.
```

If you also moved the four farm zones, update the matching coordinates in
`farm_twin_poc/zone_monitor_node.py` (`FARM_ZONES`) and
`farm_twin_poc/navigator_node.py` (`WAYPOINTS`), and reseed AMCL by
editing `initial_pose` in `config/nav2_sim.yaml` (or override `x_pose:=` /
`y_pose:=` at launch). The spawn must sit in a free cell of the baked map.

## Troubleshooting

- **Nav2 crashes with `undefined symbol: ... fastcdr ...`** inside the
  `turtlebot3_container` Docker image — `export
  RMW_IMPLEMENTATION=rmw_cyclonedds_cpp` before launching.
- **AMCL puts the robot in the wrong spot** — the spawn pose, AMCL
  `initial_pose` and the navigator's `home_x/home_y` must all match, and
  the spawn cell must be free in `maps/new_world_map.pgm`. Re-bake the map
  if you edited the world.
- **Robot stops mid-tour** — usually the GPU-less Gazebo starving the
  sim clock. Re-launch with `headless:=true`.
- **`/start_navigation` rejected with "Battery too low"** — the
  dispatcher refuses to start when the level is already below 20 %.
  Set the battery higher in the UI first, then click Start.
- **Browser shows "Failed: /start_navigation not available"** — the
  DE launch raced the PE; wait until Nav2 is active and try again.
- **Mission stays at "Idle" after clicking Start** — open the browser
  console; if you see `/api/stream disconnected` then the web server
  crashed (check Terminal B). Refreshing the tab reconnects.
