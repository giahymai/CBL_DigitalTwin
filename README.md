## What this PoC is

The Farm Twin proposes autonomous robots that detect Striga-infested zones
(spray herbicide) and low-NPK zones (apply fertilizer) on Kenyan maize farms.
Each robot is governed by a **Digital Entity** that mirrors the robot's
state and decides what to do next.

In this PoC the two entities are:

- **Physical Entity (PE):** a TurtleBot3 Burger inside a Gazebo simulation of
  the farm (`worlds/new_world.world`). It carries a LiDAR, drives under Nav2,
  and triggers `spray` / `fertilize` actions when it reaches a farm zone.
- **Digital Entity (DE):** a browser-based web interface that subscribes to
  every relevant ROS topic and renders the farm + robot live on an HTML
  canvas — the same view a remote operator would see.

The simulator stands in for the real robot, the web interface stands in for
the operator-facing dashboard, and the link between them (ROS 2 topics → an
in-process HTTP server → the browser) is the digital twin.

## Prerequisites

- ROS 2 **Jazzy** (the project targets the TB3 Burger Jazzy stack)
- `turtlebot3_gazebo`, `turtlebot3_navigation2`, `ros_gz_sim`, `nav2`
- Python 3 (only the standard library — the helper scripts and the web
  server use nothing else)

If you run inside the `turtlebot3_container` Docker image, export this
before every launch — the image ships ABI-mismatched FastDDS packages that
crash Nav2 unless you switch RMW:

```bash
export RMW_IMPLEMENTATION=rmw_cyclonedds_cpp
```

## Running in Docker (Windows + WSL2)

Start the container with `-p 8080:8080` so the web server's port is
forwarded from the container to the WSL2 host. WSL2 then proxies that
to Windows automatically, so a Windows browser hits the page at
`http://localhost:8080`:

```bash
docker run --rm -it --name turtlebot3_container -p 8080:8080 \
  -e DISPLAY=$DISPLAY \
  -v /tmp/.X11-unix:/tmp/.X11-unix \
  -v /home/c2irr10/turtlebot3_ws:/ws \
  --user $(id -u):$(id -g) turtlebot3_ws bash
```

X11 (Gazebo/RViz GUI) still works because the X server's Unix socket
is mounted in via `/tmp/.X11-unix`, which is filesystem-level and
doesn't depend on host networking. If you also need ROS 2 nodes
outside the container to discover nodes inside it, swap `-p 8080:8080`
back for `--net=host` — the two are mutually exclusive (Docker ignores
`-p` when host networking is active).

Every additional terminal joins the same container:

```bash
docker exec -it turtlebot3_container bash
cd /ws
source /opt/ros/jazzy/setup.bash
source /opt/turtlebot3_ws/install/setup.bash
source install/setup.bash
export TURTLEBOT3_MODEL=burger
export RMW_IMPLEMENTATION=rmw_cyclonedds_cpp
```

### Reaching the web interface from your Windows browser

Inside the container, in a second terminal:

```bash
ros2 run farm_twin_poc web_server_node
# logs: web_server_node up — http://0.0.0.0:8080/
```

On Windows, open:

```
http://localhost:8080
```

That's it — `-p 8080:8080` puts the container's port 8080 on the WSL2
host, and WSL2 proxies localhost to Windows automatically.

If `localhost` doesn't work on older WSL2 setups, find the WSL IP from
a PowerShell window and use that instead:

```powershell
wsl hostname -I
# then in browser: http://<that-ip>:8080
```

To verify before troubleshooting Windows, hit the API from inside WSL:

```bash
curl http://localhost:8080/api/topics
```

## Launch the Physical Entity (Gazebo + Nav2)

Single command brings up Gazebo, the TB3 spawn, Nav2 (with AMCL seeded at
the spawn pose), the navigator, the zone monitor and the DT logger:

```bash
ros2 launch farm_twin_poc gazebo_nav2_demo.launch.py
```

Useful overrides:

```bash
# headless = Gazebo server only (no 3D GUI). Recommended on GPU-less
# machines (Docker-in-WSL, etc.) where the GUI starves the sim clock.
ros2 launch farm_twin_poc gazebo_nav2_demo.launch.py headless:=true

# pick a different spawn / map / world
ros2 launch farm_twin_poc gazebo_nav2_demo.launch.py \
    x_pose:=0.5 y_pose:=-2.5 map:=$HOME/my_map.yaml
```

When RViz reports **Nav2 is active**, start the zone tour:

```bash
ros2 service call /start_navigation std_srvs/srv/Trigger
```

The robot drives A → B → D → C (S-curve, shortest path). At each zone it
pauses, spins 360°, and `/farm_action` fires with `spray` or `fertilize`.

## Launch the Digital Entity (Web Interface)

There are two ways to view the DE — pick one.

### Live mode (subscribes to ROS)

In another shell with the same `source install/setup.bash`:

```bash
ros2 run farm_twin_poc web_server_node
# open http://localhost:8080
```

The node subscribes to every relevant topic (`/odom`, `/amcl_pose`, `/scan`,
`/cmd_vel`, `/plan`, `/map`, `/farm_action`, …) and serves both the static
web files and a JSON API:

```
GET /                  -> web/index.html
GET /api/state         -> all cached topics as JSON
GET /api/state/<name>  -> one topic (e.g. /api/state/odom)
GET /api/topics        -> list of cached topic names
```

Override host/port with `--ros-args -p host:=0.0.0.0 -p port:=8080`.

### Standalone mode (no ROS, no server)

`web/app.js` ships with the world geometry inlined — just open the file:

```bash
open web/index.html        # macOS
xdg-open web/index.html    # Linux
```

The canvas renders the walls + four zones from `MAP` (a JSON literal at the
top of `app.js`). Useful for previewing UI changes without bringing up the
sim.

## After editing the world

`worlds/new_world.world` is the single source of truth for the walls and
zone positions. If you move things in it, regenerate the two derived
artifacts:

```bash
# 1) Nav2 occupancy grid for AMCL / costmap
python3 scripts/world_to_map.py worlds/new_world.world
# -> maps/new_world_map.{pgm,yaml}

# 2) Canvas geometry for the web interface
python3 scripts/world_to_canvas.py worlds/new_world.world
# -> web/map.json
# Then paste web/map.json into the MAP constant in web/app.js if you want
# the standalone (file://) mode to reflect the change.
```

If you also moved the four farm zones, update the matching coordinates in
`farm_twin_poc/zone_monitor_node.py` (`FARM_ZONES`) and
`farm_twin_poc/navigator_node.py` (`WAYPOINTS`), and reseed AMCL by
editing `initial_pose` in `config/nav2_sim.yaml` (or override `x_pose:=` /
`y_pose:=` at launch). The spawn must sit in a free cell of the baked map.

## Evidence that the PoC works

| Goal | How to see it |
|---|---|
| PE → DE telemetry | `ros2 topic echo /scan --once`; the same arc shows up on the canvas |
| DE → PE commands | `ros2 topic echo /cmd_vel`; the canvas robot moves with it |
| Zone trigger | `ros2 topic echo /farm_action` while the tour runs |
| Twin sync | `/api/state/odom` and `/api/state/amcl_pose` agree to within AMCL noise |

## Troubleshooting

- **Nav2 crashes with `undefined symbol: ... fastcdr ...`** inside the
  `turtlebot3_container` Docker image — `export
  RMW_IMPLEMENTATION=rmw_cyclonedds_cpp` before launching (the image's
  FastDDS stack has ABI-mismatched packages).
- **AMCL puts the robot in the wrong spot** — the spawn pose, AMCL
  `initial_pose` and the navigator's `home_x/home_y` must all match, and
  the spawn cell must be free in `maps/new_world_map.pgm`. Re-bake the map
  if you edited the world.
- **Robot stops mid-tour** — usually the GPU-less Gazebo starving the
  sim clock. Re-launch with `headless:=true`.
